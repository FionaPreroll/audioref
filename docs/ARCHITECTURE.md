# Architecture

How AudioRef is built inside: its crates, its threads and the path of the signal. Parts marked *planned* come with the next steps of [PLAN.md](PLAN.md#next-steps).

## Crates

| Crate | Holds | Depends on |
|---|---|---|
| `crates/audioref-core` | The logic as plain Rust: the texts (`i18n`), the saved correction (`state`), the signal processing (`engine`, `gain`, the channels and the crossfeed in `stereo`, the `limiter`, the filters in `biquad`, `cascade` and `convolver`, one of them as a `filter`), parametric EQs with the ranges of their values (`eq`), OPRA's database (`opra`) and the copy of it built in (`bundled`), AutoEQ's curves (`autoeq`) and the addresses and name index of its files (`profiles`), the design of a correction from them (`design`) and its minimum-phase or linear-phase filter (`fir`), the delay lines that keep the paths in line with it (`delay`), what the about window lists of the build (`about`), and what the dialog that picks a file asks for (`browse`) | No crate with plugin APIs, GUI or I/O; `make lint` checks it |
| `crates/audioref` | The plugin: nih-plug, the parameters, the language of the system, the window (`editor`, with egui), reading OPRA's file and designing the corrections in the background (`background`), the system's dialog that picks a file (`browse`), the saved state, and the about window (`about`, with `build.rs`, which also packs the built-in database) | `audioref-core`, nih-plug, nih_plug_egui, rtrb, sys-locale, rfd; `audioref-core` for `build.rs` too |
| `xtask` | The bundler, `cargo xtask bundle audioref --release`, and `cargo xtask fetch-profiles`, which downloads headphone data with curl into a folder outside the repository, see [Fetching the files](../README.md#fetching-the-files) | nih-plug's xtask, `audioref-core` |
| `fuzz` | The fuzz targets, a workspace of its own, see [fuzz/README.md](../fuzz/README.md) | `audioref-core`, libfuzzer-sys |
| `screenshots` | The plugin as a standalone program, for screenshots of the window, a workspace of its own, see Screenshots in [DEVELOPMENT.md](DEVELOPMENT.md#screenshots) | `audioref`, nih-plug's standalone host |

The core can be tested without a host, to 100 % of its lines and functions. The plugin crate only translates between nih-plug and the core.

## Threads

```text
 GUI thread (editor)            background                         audio thread
 ───────────────────            ────────────────────               ────────────
 pick headphones, mode,  ──▶    read OPRA's file,          ──▶     channels → crossfeed
 target, controls               design the filters                 → correction → level
                                                                   → limiter
                                (core: opra, biquad,       lock-free (core: engine,
                                 cascade)                  hand-over  cascade)
```

- The audio thread never allocates, locks or reads files. Filters are designed in the background and handed over without locks; the old ones go back to be freed outside the audio thread.
- A new correction cross-fades from the one before for 20 ms, like the level and the bypass (`audioref_core::engine`). The engine keeps the correction before until the next one comes, and hands it back then, so it never frees one itself.
- The window saves the chosen preset and asks the background, a thread of the plugin's own, to design it for the current sample rate (`crates/audioref/src/background.rs`). nih-plug's background thread isn't used: the executor nih-plug hands to the editor holds the plugin's wrapper, so an editor that kept it would keep the plugin alive, and nih-plug's thread would still run when the host unloads the library, which crashes the host on Windows. AudioRef's thread starts with the plugin and is joined when the host frees it. The background sends the filter, the cascade of a preset or the FIR of a designed correction (`audioref_core::filter`), through a lock-free queue (rtrb) to the audio thread, which takes it at the start of the next block, and gets the old one back through a second queue to free it. The audio thread takes a correction only while the queue back has room, and leaves out one designed for another sample rate.
- When the host activates the plugin, e.g. with a new sample rate or after loading a project, `initialize` empties the queue and designs the saved correction itself, outside the audio thread, so the first block has it.
- **Browse…** opens the system's dialog that picks a file (`crates/audioref/src/browse.rs`, with rfd), which must not hold up the host. On Windows and Linux it runs on a thread of its own, which notes the file in a mutex of `Shared`; the window looks at it in each frame, puts the file into its field and loads it, as **Load** would. The window's thread goes on drawing meanwhile, and as it never waits in the middle of a frame, no message of the host reaches it there. That thread is joined when `Shared` is dropped, with the plugin and the window, so it never outlives the library; if the dialog is still open then, the host waits until it is closed. macOS shows dialogs only from the main thread, which the window runs on: there the dialog is modal, as usual on macOS, but never inside a frame. baseview holds the window's handler while egui draws, and the modal loop of the dialog hands the window events, which baseview can't give the handler then, so it panicked ("`RefCell` already borrowed") and took Bitwig's plugin host down. The frame therefore only queues the dialog on the main queue of Grand Central Dispatch (dispatch2), and it runs once the frame is over. On Linux, rfd asks the XDG desktop portal through D-Bus, loaded at run time, or else runs zenity, so the plugin links no GTK.
- Only the window and the background lock the mutexes of `Shared`: OPRA's database, and the ends of the queues they hold. The audio thread never does.

## The signal

Stereo in, stereo out, with a latency of 0 samples, or with linear phase that of the linear-phase filter, see [Linear phase](#linear-phase). In this order, the parts not built yet marked *planned*:

1. The channels as they are, in mono (both at half the level in both ears) or swapped, and the crossfeed, off or in three strengths (`audioref_core::stereo`). The crossfeed follows Bauer's idea, as bs2b does, in a form that leaves the middle alone: a first-order lowpass at 700 Hz of the difference of the channels, taken from the left and added to the right, `L' = L − g·LP(L − R)`, `R' = R + g·LP(L − R)`. What both channels share passes unchanged; below the lowpass each ear hears the other channel 9.5, 6 or 4.5 dB below its own (Jan Meier's, Chu Moy's and bs2b's levels), above it less and less. The lowpass gives the crossfed part a delay of about 0.2 ms, near the time sound takes around the head. As the correction is the same in both channels, it doesn't matter whether this stage comes before or after it. A change of the routing or the strength fades over 20 ms.
2. Automatic headroom: the overall gain of the correction is lowered by its largest boost between 20 Hz and 20 kHz, on AutoEQ's grid, so it boosts nothing (`audioref_core::cascade`). Most of OPRA's presets bring enough of their own; the most any needs is 5.4 dB.
3. The correction: a cascade of biquads for OPRA's presets (`audioref_core::cascade`), computed with 64 bits, or the minimum-phase FIR of a correction designed from AutoEQ's curves (`audioref_core::fir`, see [Designing a correction](#designing-a-correction)), computed with 32 bits and convolved without latency (`audioref_core::convolver`): the first 128 taps in the time domain, sample by sample, the others in partitions of 128 taps with FFTs of 256 points, whose share of a block depends only on the blocks before, so it is ready when the block starts. The FFTs work in buffers made with the filter, so the audio thread doesn't allocate. On one core of the sandbox, both channels take 1.2 % at 48 kHz (4096 taps), 2.2 % at 96 kHz and 5.8 % at 192 kHz (16384 taps).
   The biquads follow Vicanek's matched design (`audioref_core::biquad`), as the usual formulas bend above about 10 kHz at 44.1 kHz: the poles of the analog filter, and zeros that give the analog magnitude at 0 Hz, at the band's frequency and at half the sample rate. Peaks and shelves up to 10 kHz stay within 0.75 dB of the analog filter up to half the sample rate. Bands at or above half the sample rate are left out.
4. The output level and the bypass, both faded over 20 ms (`audioref_core::engine`), the length adapted to the sample rate.
5. The limiter (`audioref_core::limiter`), on by default: both channels together stay at or below −0.3 dBFS, the peak of their samples. It has no lookahead, so no latency: when a sample would go above the ceiling, the gain drops at once to just what keeps it there, and comes back with a time constant of 100 ms. Off, it only lets the gain come back, so turning it off doesn't click. The bypass fades to the unprocessed input, around the limiter too.
   The audio thread notes the most it lowered the signal in each block in an atomic of `Shared`, keeping the largest until the window takes it, so no lock is needed. In the same way it notes the peak of the output's samples, after the limiter (`Engine::take_peak`). The window draws itself 30 times a second, holds both values and lets the reduction fall by 10 dB and the level by 20 dB per second. A click on either bar turns both displays off, for slow graphics (`meters`, saved with the project): the window then takes the values without showing them and is only drawn again when egui needs it, e.g. for the pointer.

## Linear phase

With the setting `linear-phase` (`audioref_core::filter::Phase`), the background makes every correction a linear-phase FIR instead (`Filter::of_eq`, `Filter::of_correction`): for a preset of the cascade's response, so the level at each frequency is that of the biquads, for a design of the correction lowered by its headroom. `audioref_core::fir::linear_phase` samples the response on a grid 8 times as fine as the filter, transforms its magnitude back without phase, which gives the zero-phase impulse response, centred on 0, and delays it by its latency, half the taps less one (2047 samples at 48 kHz, 43 ms at 48, 96 and 192 kHz and 46 ms at 44.1, 88.2 and 176.4 kHz), faded out over the outer eighths of both halves. It has as many taps as the minimum-phase filter and runs in the same convolver, so it costs as much; it follows the correction within 0.5 dB from 30 Hz.

The engine delays every path by the latency (`Engine::set_latency`, `audioref_core::delay`): the unchanged signal of the bypass, the signal without a correction, and each correction by the latency less its own. So the fades between corrections, the bypass, and a minimum-phase correction still running while the linear-phase one is designed, all stay in line. The plugin sets the latency in `initialize` and, when the setting changes, at the start of the next block, and reports it to the host (`set_latency_samples`), which makes up for it in playback; the window designs the correction again, in the new phase. Live input is heard late by as much.

## Headphone data

`audioref_core::opra` reads the text of OPRA's `database_v1.jsonl`, about 12 MB with some 19,500 lines, in about 0.1 s: its vendors, products and EQ presets, each by its ID. OPRA lists the modes of some headphones as products of their own, e.g. "WH-1000XM4 (ANC on)".
A line it doesn't understand, e.g. of a kind a later OPRA adds, a band type it doesn't know or a value outside the ranges of `audioref_core::eq`, is left out and counted, so one bad line doesn't cost the others. The ranges hold for every EQ that reaches the filters: frequencies from 1 Hz to 100 kHz, band gains of ±30 dB, Qs from 0.1 to 100, an overall gain from −60 to +30 dB, and at most 32 bands, the first ones, as OPRA sorts them by priority.
The plugin reads the file in the background, and the window shows each preset's author, as OPRA's license (CC BY-SA 4.0) asks.

Without a file, the window uses the presets built into the plugin (`audioref_core::bundled`): OPRA's whole database, `data/opra/database_v1.jsonl`, unchanged. `crates/audioref/build.rs` packs its 12.6 MB with deflate (miniz_oxide), to 1.2 MB, which the plugin includes with `include_bytes!`. When the plugin starts, its background thread unpacks and parses it, in about a tenth of a second (`bundled::database`, at most 256 MiB unpacked); until then the list says "Loading…". All instances of AudioRef in a host share the parsed database through a `Weak` in a static (`background::built_in`), so it is parsed once and freed with the last instance. When a file can't be read, the window says so and keeps the built-in presets; loading with an empty path goes back to them. `data/opra/README.md` names the source, the commit and the authors; `utils/update-opra-database.py` puts a newer database there, and the tests check that every line of it is understood.

`audioref_core::autoeq` reads measurements and targets in AutoEQ's CSV format, a header `frequency,raw` and one line per frequency, and what other tools write: more columns (it takes `raw`, or else the column after the frequency), no header, `;` with a decimal comma, tabs or spaces, comments starting with `#` or `*`. Like OPRA's database, a line it doesn't understand is left out and counted. A curve has from 2 to 100,000 points with rising frequencies from 1 Hz to 100 kHz and levels of ±200 dB, so sound pressure levels pass too, and must reach from 100 Hz to 10 kHz; between its points the level runs straight on a logarithmic frequency axis, and beyond its ends it stays flat. The fuzz target `autoeq_curve` reads it.

`cargo xtask fetch-profiles` fetches these files from OPRA's and AutoEQ's repositories, their main branches, with curl, into a folder outside the repository (`xtask/src/profiles.rs`): OPRA's database, AutoEQ's Harman over-ear 2018 target, and oratory1990's measurements of the headphones named. It finds a measurement through AutoEQ's `measurements/oratory1990/name_index.tsv` (`audioref_core::profiles`): tab-separated lines of the PDF's address, oratory1990's name, AutoEQ's name, the form (`over-ear`, `in-ear`, `earbud`, or `ignore` for those AutoEQ leaves out) and the rig. A name fits a model whose name, either one, it is in any case, or else the only one whose name contains it. The file is saved under AutoEQ's name, without the characters that systems don't allow or that would leave the folder. Each file is downloaded next to its place first, then read with AudioRef's own parsers, so a change of a format upstream shows at once. The fuzz target `name_index` reads the index.

## Designing a correction

`audioref_core::design` computes a correction from a measurement and a target, on AutoEQ's grid of 1.01 steps from 20 Hz to 20 kHz:

1. Correction = target + tilt + bass shelf − measurement. The tilt goes from −1 to +1 dB per octave around 1 kHz; the bass shelf, from −6 to +12 dB, is the Harman target's: half its gain at 105 Hz, Q 0.71.
2. Smoothing: over 1/12 octave up to 2 kHz, wider above, 1/3 octave from 8 kHz, so narrow peaks and dips of a single measurement, which move with the fit, aren't copied.
3. Set to 0 dB on average from 200 Hz to 2 kHz.
4. Faded out from 12 to 16 kHz with a raised cosine, nothing above: up there, measurements depend on the ear and the fit more than on the headphones.
5. Limits: boosts up to +6 dB by default (0 to 12 dB), cuts to −30 dB.
6. *Planned:* a warning when the target doesn't fit the rig of the measurement.

`audioref_core::fir` makes the minimum-phase filter of a correction, by the real cepstrum, with FFTs 8 times as long as the filter (realfft): 4096 taps at 44.1 and 48 kHz, 8192 at 88.2 and 96 kHz, 16384 at 176.4 and 192 kHz, the last eighth faded out. Its overall gain is lowered by the largest boost, so it boosts nothing, like the cascade's. It follows the correction within 0.5 dB from 30 Hz to 20 kHz at every sample rate, and puts 98 % of its energy into the first 2 ms. It takes 2 to 10 ms, so it runs in the background.

## Render guard

With "Bypass on export" on, the default, AudioRef bypasses itself while the host processes offline (`audioref_core::render`). Hosts activate the plugin again whenever that changes, with `ProcessMode::Offline` in nih-plug, so the bypass is in place from the first sample of an export, without a fade. In the VST3 version this needs the fork of nih-plug, which hands `initialize` the mode the host just set, see Dependencies in [PLAN.md](PLAN.md#dependencies). The parameter `bypass_on_export` is saved with the project, but isn't automatable.
Hosts that export in real time don't say so, which is why the window also shows the notice to bypass AudioRef before exporting. Bitwig 6 exports offline: there the export came out as expected with the VST3 and the CLAP alike (Fiona, 2026-11-08). FL Studio was tested on Windows too; see Tested in DAWs in [PLAN.md](PLAN.md#tested-in-daws).

## Window

`crates/audioref/src/editor.rs` draws the window with egui, through nih_plug_egui, in the system's language. `crates/audioref/src/theme.rs` gives it its look when it opens: the colors, the sizes of the fonts, the spacing and the round corners of egui's style, and the cards, framed parts of the window with a title, that the parts below sit in. At the top are the name, the tabs for where the correction comes from, and **About**:

- **OPRA presets:** the search for headphones, how many presets the list holds and from where, the headphones and the presets of the chosen ones, and below them OPRA's file in a section that folds away, open while a path is set or a file failed to load, with **Browse…**, which picks the file with the system's dialog, see [Threads](#threads), and **Load**. When the window opens, it chooses the headphones of the saved preset again (`Database::product_of`), and searches for their name if the list without a search wouldn't show them. nih-plug creates the editor with the plugin, before the host restores the project, so each time the window opens it takes the saved state anew (`opened` in `editor.rs`): the tab of the current correction, the paths in the fields, and the files the project names, OPRA's and those of the measurement and the target, which it reads again unless they are loaded (`Task::Reload`, `Task::ReloadCurve`). These fail softly: OPRA's file that can't be read again leaves the built-in presets with a note in grey (`Load::Unavailable`), and is tried again the next time the window opens; a curve leaves its field without a message, as the design is saved with the project.
- **Own curves (AutoEQ):** the files of a measurement and a target, each with **Browse…** and **Load**, each read in the background, with its name and number of points or why it can't be used beside it, and the button that makes them the correction.

At the top right of the correction's card, the switch **Linear phase**, with the latency while it is on, see [Linear phase](#linear-phase). Below the tabs the current correction: for a preset its author ("EQ by …, from OPRA, CC BY-SA 4.0", and a link to OPRA's repository, as OPRA asks), for a design the names of the measurement and the target and the sliders of the tilt, the bass and the limit for boosts; then the curve from 20 Hz to 20 kHz, taking the height left, with a grid at 2, 5 and 10 times each decade and every 6 dB, the area to 0 dB filled, the headroom beside the label of 0 dB, and under the pointer the level at the nearest frequency (`Message::CurvePoint`); at the bottom the parameters in three cards side by side, output, stereo and protection (the output level, the bypasses, and lists for the channels and the crossfeed, whose names the host shows too, the output's peak level with its bar from −60 to 0 dBFS, the limiter with its bar from 0 to 12 dB), and the notices. The curve follows a slider at once, designed in the window; the filter is designed in the background once the slider is let go, as that takes up to 10 ms. Every control has a hint, shown when the pointer rests on it, and where the window waits for something it says what to do next: to pick headphones, to load both curves before using them, or to lower the output level when the limiter lowers the signal by 3 dB or more (`audioref_core::i18n::Hint`). The window only reads and shows; the search, the texts and the curve's values come from the core.

The name "AudioRef" at the top left and the button at the top right open the about window (`crates/audioref/src/about.rs`): the version, the plugin format the host loaded (CLAP or VST3, from `GuiContext::plugin_api` of nih-plug), the git commit and the time of the build, whether GitHub Actions built it, the contact, the homepage, the link to the releases, AudioRef's license and that of the built-in presets, "Written in Rust", and the crates AudioRef is built with, each with its license and, opened, its license texts. `crates/audioref/build.rs` collects them when the plugin is built:

- the commit from `git rev-parse HEAD`, else `GITHUB_SHA`; the time from `SOURCE_DATE_EPOCH`, else the clock;
- the run of GitHub Actions, its number and the address of its page, from `GITHUB_ACTIONS`, `GITHUB_SERVER_URL`, `GITHUB_REPOSITORY`, `GITHUB_RUN_ID` and `GITHUB_RUN_NUMBER` (`audioref_core::about::ci_run`); outside GitHub Actions the window says that it was built elsewhere;
- the crates from `cargo metadata --offline --filter-platform <target>`: those the plugin reaches through normal dependencies, not those for building or development only, without the workspace's own (`audioref_core::about::packages`);
- their license files (`LICENSE*`, `COPYING`, `NOTICE`, a font's `OFL.txt` and the like, `audioref_core::about::is_license_file`), at the top of the crate and in the folders in it, or for a crate of a git repository without any, at the top of the repository; a crate with none at all, e.g. egui, gets the standard text of its license from `crates/audioref/licenses/` (MIT, Apache-2.0, ISC) with its name and authors;
- each text once, written as Rust into `third_party.rs` in `OUT_DIR`, which `about.rs` includes. That adds about 400 KB to the plugin.

Nothing there fails the build: without git the commit shows as unknown, and if `cargo metadata` fails, the window says that the build has no list. The fuzz target `cargo_metadata` reads `cargo metadata`'s output.

On Linux, the window needs X11 and OpenGL; `utils/install-linux-deps.sh` installs the libraries to build it.

## Saved state

The project saves, besides the parameters:

- `correction`: the chosen preset with its bands, author and headphones (`audioref_core::state::SavedCorrection`), so a project opens with its correction on a computer without OPRA's file. nih-plug stores it as JSON; its values are checked again before they are used, and the fuzz target `saved_correction` reads it.
- `opra-path`: the path of OPRA's file, which the window loads again when it opens; empty for the built-in presets.
- `design`: a correction designed from a measurement and a target (`audioref_core::state::SavedDesign`): their names, both curves on AutoEQ's grid, and the tilt, the bass and the limit for boosts, so a project opens with its correction without the files and the settings can still change. If there is one, it is the correction, not the preset; choosing a preset removes it, and using a design removes the preset. The fuzz target `saved_design` reads it.
- `measurement-path`, `target-path`: the paths of the files of the measurement and the target, for the window's fields.
- `meters`: whether the window shows the level and the limiter's reduction; on unless turned off by a click on a bar.
- `linear-phase`: whether the corrections are linear-phase, off by default, see [Linear phase](#linear-phase). A setting, not a parameter, so hosts don't automate the latency.
- `editor-state`: the size of the window.

Parameter IDs and these keys never change; the names of the parameters and of the choices of `channels` and `crossfeed` are in the system's language, and hosts that let users type a value take a name in either language or its index.
